# M5: advertiser portal

Built on the approved routing change (real portal pages, commit `495ccb8`). See [ROUTING_PROPOSAL.md](ROUTING_PROPOSAL.md) for its evidence.

## What changed

### Stepped campaign flow (decision D2: on the live APIs)

`/advertiser/create-campaign` is now three steps with a progress rail (the route-line motif):

1. **Name and creative.** Campaign name, plus the creative chosen from cards that show each creative's placement and review status. If there are no creatives, an empty state links to the creative library.
2. **Schedule.** First and last day (up to 60 days), daily start and end time, days of the week.
3. **Review.** A summary with a "Change" link per item, a warning if the creative isn't approved yet, and **Save campaign draft**.

- **Per-step validation:** "Continue" checks the current step and shows each error next to its field ("Enter a campaign name.", "The last day must be on or after the first day.", "A campaign can run for up to 60 days…", "Choose at least one day of the week.", "The daily end time must be later than the start time."). Completed steps can be revisited from the rail. Focus moves to the step heading when the step changes.
- **Save and resume:** the draft is saved on the server (`POST /campaigns`). Opening a draft (`/advertiser/campaigns/[id]`) resumes the same flow on its review step. You can change any step, **Save draft changes** (`PATCH`, with the revision check), then **Submit for review**. Submit is disabled while there are unsaved changes. Non-editable campaigns (in review, approved…) show a read-only summary. Browser storage is not used; `tests/b3-advertiser-live-contract.test.mjs` forbids it here.
- **Not added:** location, screen and price selection inside the flow. The live campaign API doesn't take them; screens and prices are chosen when requesting a quote in Billing and payments, which the campaign page links to. The legacy six-step wizard's checkout steps are not revived (no demo stores).

### Other screens

- **Dashboard:** a "next step" card (add a business, then upload a creative, then create a draft), four metrics with tabular numbers and an honest note, and a recent-campaigns table.
- **Campaigns:** a status filter (segmented control) and a table with status badges.
- **Creative library:** a three-stage indicator (upload, processing, send for review), labelled fields, plain-language placements and statuses, reviewer feedback shown.
- **Settings, locations, ad formats, billing, reports, notifications, support:** restyled through the shared advertiser blocks (`Panel`, `Notice`, fields, buttons, pagination, empty states), which now use the design system. Engineering-facing wording was rewritten, for example "Account updated from backend." became "Profile saved."; "Get live quote" became "Request a quote"; "…belong to Part 6… Cashfree checkout…" became "Online payment isn't available here yet…".
- Statuses everywhere use `StatusTag`: `draft` reads "Draft", `submitted` reads "In review", `changes_requested` reads "Changes requested" and so on, each with a coloured dot.
- The segmented control (`Tabs`) is 44 px tall on phones (it was 36 px).

### Robustness fix found during testing

The new placement label crashed when a creative record had no `placement` (the CI browser mock omits it), sending the page to the error screen. `placementLabel` and `StatusTag` now handle missing values.

## Not verified

- Uploading a real file end to end: the creative upload needs object storage and a processing worker, which are mocked or absent here. The upload code is unchanged apart from layout and messages.
- Quotes and payments with real data (no published screens or rate cards locally).
- The deployed site, real phones, Safari and Firefox.
- `operations.tsx` and `common.tsx` were not run through Prettier: their dense style holds exact-text security checks, so only their content changed.
