# M6: driver portal

Scope approved by the owner: purpose-built screens **and** the driver application on the live API, with an honest locked state where the live setup can't support a step yet.

## What changed

The generic record viewer (`ApiSection`, which printed IDs, `["driver"]` and raw values) is replaced by screens in `src/features/driver-live/`. Each driver page renders its own screen. No `JSON.stringify` output remains in the driver portal.

| Page | Screen |
|---|---|
| Today (`/driver`) | Greeting, a status line (route-line motif: apply, verification, screen installed, ad assignments) with the next action, today's assignment (honest "not available yet"), earnings at a glance |
| Onboarding | **New: the driver application on the live API.** Start an application, then: 1 city and experience; 2 choose a vehicle (links to Vehicle if none); 3 screen placement for that vehicle type. Each step validates, saves on the server and can be changed later. Steps 4 (partner agreement) and 5 (final check and submit) are locked with an explanation. Submitted, approved, rejected and changes-requested states each get a summary. |
| Verification status | Checklist: application details, vehicle checked, documents (listed if any exist; otherwise an explanation that upload isn't available in the portal yet), submitted, approved |
| Vehicle and screen | Vehicles with check status; **new: add a vehicle** (type, make and model, year). The number plate is deliberately not asked for. |
| Earnings | Available, total earned, paid out and in-a-payout amounts (tabular rupees), with the earning entries. Read-only. |
| Payout history | Settlements with period, amount and status. Read-only, with a note that bank payouts aren't switched on. |
| Maintenance and issues | Screen problem cases with status; links to Support to report one |
| Notifications | Unread notifications highlighted; "Mark as read" |
| Support | Contact form (general question, or screen problem with the screen ID), ticket list with status, reply to a ticket |
| Profile and documents | Name, email, city, account status |
| Assigned ads, Campaigns, Screen activity, Trips | Honest empty state: not available in the portal yet. **No API call** (the old screens called `/driver/assignments`, which the backend doesn't serve, and showed "API route not found"). |

- Mobile-first: content columns are at most about 720 px wide, primary actions are full width on phones, choices are large radio cards, and every tap target on phones is at least 44 px.
- Breadcrumb links in the shared page header are now 44 px tall on phones (all portals).
- The driver portal no longer shows the engineering description under each title, and the home page is titled "Today" (the menu label changed from "Dashboard").

## Why steps 4–5, documents and submission are locked

- **Step 4** records which partner agreement version the driver accepted. No agreement is published, and inventing a version string for a legal document would be wrong.
- **Document upload** needs private storage (`KYC_S3_*`), which isn't configured on the live setup.
- **Submission** requires all five steps.

When those exist, the onboarding screen can enable them; the backend already supports them.

## Verification

**Real backend, real database, as the audit driver account at 390 px:**

| Request | Result | Headers |
|---|---|---|
| `POST /drivers/applications` `{}` | 201 | CSRF, idempotency key |
| `PATCH /drivers/applications/:id` step 1 `{city, experience}` | 200 | CSRF |
| `POST /drivers/me/vehicles` `{type, model, year}` | 201 | CSRF, idempotency key |
| `PATCH …` step 2 `{vehicleId, vehicleCategory}` | 200 | CSRF |
| `PATCH …` step 3 `{screenChoice}` | 200 | CSRF |
| `POST /support/tickets` `{category, subject, description}` | 201 | CSRF, idempotency key (same body shape as before) |

The database then held the application as `DRAFT`, 3 steps complete, with the chosen city, experience, vehicle category and screen. Saving step 1 empty showed both field errors; step 4 showed the locked explanation; Today showed "3 of 5 steps done". Each `PATCH` sends the `expectedVersion` the backend checks; a version conflict reloads the application and says so.

**All 14 driver pages at 360, 390 and 1440 px (real backend):** 0 axe violations, no horizontal overflow, no console errors, no failed API requests, no raw JSON, and no tap targets under 44 px on phones.

**Other checks:** full CI sequence; all tests in `tests/`; `test:portal-shell` 18/18; `b22-live-browser` 3/3; `b2-auth-browser`; `test:visual`; the 60-route crawl shows the access matrix unchanged (only the driver home title changed, "Overview" to "Today"), no overflow and no page errors. One route, `/admin/users`, shows one more low-contrast element than in M5. It's the existing pale grey text M1 recorded there, and the list now has one more row (a test admin account created locally); M7 replaces that screen.

## Tests changed

- `scripts/b22-live-browser.mjs` (driver part): waited for the old raw label "Earned Paise" and clicked a generic "Manage" button. It now waits for the rupee amount (`₹220.00`, i.e. the mock's 22000 paise) and clicks "Mark as read", then still asserts the `POST …/read` request.
- `scripts/portal-shell-browser.mjs`: the driver home title is now "Today".
- No security assertion changed. `src/features/live/api-portal.tsx` keeps the session, revalidation, 401 handling, CSRF and idempotency code the contract tests check; it now also exports `useApiPortal()` for the driver screens.
